# アセンブラ 3. つまずきポイントと解き方

[← 前: 命令と読み方](02-reading.md) | [目次](../index.md)

---

初めてアセンブリを読むときに、多くの人が引っかかるポイントをまとめました。各項目は「症状 → 原因 → 解き方」の順に書いています。

## 3.1 オペランドの向きが逆に見える

**症状**: `mov %rax, %rbx` を「rax に rbx を入れる」と読んでしまい、全体の意味が合わない。

**原因**: AT&T 構文は「読み込み元, 書き込み先」、Intel 構文は「書き込み先, 読み込み元」で、向きが逆です。

**解き方**

- `%` と `$` が付いていたら AT&T 構文、と最初に確認します。
- 慣れるまでは、Intel 構文に揃えて出力します（`gcc -masm=intel`、`objdump -M intel`、GDB の `set disassembly-flavor intel`）。

## 3.2 `lea` をメモリ読み込みだと思ってしまう

**症状**: `lea rax, [rdi+rsi*4]` を見て、配列の要素を読んでいると思ってしまう。

**原因**: `lea` は `[...]` の中の **アドレスを計算するだけ** で、メモリは読みません。`mov` とは違います。

| 命令 | rax に入るもの | C で言うと |
|------|---------------|-----------|
| `mov rax, [rdi+rsi*8]` | そのアドレスにある値 | `rax = a[i];` |
| `lea rax, [rdi+rsi*8]` | アドレスそのもの | `rax = &a[i];` |

**解き方**: `lea` は「掛け算と足し算をまとめて 1 命令でやる計算」として使われることも多い、と覚えておきます。

```c
int f(int x) { return x * 5 + 3; }
```

```asm
; 一例（gcc -O2）
f:
    lea     eax, [rdi+rdi*4+3]     ; x + x*4 + 3 = x*5 + 3（メモリは読んでいない）
    ret
```

## 3.3 32ビットレジスタと 64ビットレジスタの関係

**症状**: `mov eax, -1` のあとに `rax` が `0xFFFFFFFFFFFFFFFF` だと思ったら、`0x00000000FFFFFFFF` だった。

**原因**: 32 ビットレジスタ（`eax` など）に書き込むと、64 ビットレジスタの上位 32 ビットは 0 になります。8 / 16 ビットレジスタ（`al`, `ax`）への書き込みでは、上位ビットは変わりません。

**解き方**

- `eax` に書いた値は「`rax` 全体に 0 拡張された」と読みます。
- 符号付きのまま 64 ビットにしたいとき、コンパイラは `movsxd`（符号拡張）を使います。`movsxd` があれば、元の型は `int` などの符号付きです。

## 3.4 符号付きと符号なしの見分け

**症状**: C のソースが無いと、変数が `int` なのか `unsigned` なのか分からない。

**解き方**: 使われている命令から判断します。

| 命令の種類 | 符号付き（`int` など） | 符号なし（`unsigned` など） |
|-----------|----------------------|---------------------------|
| 条件ジャンプ | `jl` `jg` `jle` `jge` | `jb` `ja` `jbe` `jae` |
| 右シフト | `sar` | `shr` |
| 拡張 | `movsx` / `movsxd` | `movzx`（32→64 は単なる `mov`） |
| 割り算 | `idiv` | `div` |

## 3.5 引数がどこにあるか分からない

**症状**: 関数の最初で `rcx` を使っているのに、Linux の資料では第1引数は `rdi` と書いてある。

**原因**: 呼び出し規約が OS ごとに違います。Windows の第1引数は `rcx`、Linux / macOS の第1引数は `rdi` です。

**解き方**

- まず、どの OS 向けにビルドされたバイナリか確認します（Windows なら `.exe` / `.dll`、Linux なら ELF 形式）。
- そのうえで [2.5 の表](02-reading.md) に当てはめます。

## 3.6 `call` のあとでレジスタの値が変わっている

**症状**: `call` の前に `rcx` に入れた値を、`call` のあとでも使えると思っていたら壊れていた。

**原因**: 呼ばれた関数は、「呼び出し側が保存するレジスタ」（`rax`, `rcx`, `rdx`, `r8`〜`r11` など）を自由に書き換えてよい決まりです。

**解き方**: `call` をまたいで値を残したいとき、コンパイラは `rbx` や `r12`〜`r15` など、呼び出し先が保存するレジスタを使います。関数の入口で `push rbx` などをしているのはそのためです。

## 3.7 スタックのアライメントで落ちる

**症状**: 自分で書いたアセンブリから `printf` などを呼ぶと、`movaps` 命令でクラッシュする（Segmentation fault）。

**原因**: x86-64 では、`call` を実行する直前に `rsp` が 16 バイト境界に揃っている必要があります。`call` は戻り先アドレス（8 バイト）を積むので、関数に入った直後の `rsp` は 16 の倍数から 8 ずれた状態になります。この状態のまま、さらに別の関数を呼ぶとずれたままになります。

**解き方**

- 関数に入ったら、`push` の回数と `sub rsp, N` の合計が「8 + 16 の倍数」バイトになるように調整します。
- 例：`push rbp` を 1 回（8 バイト）したら、`rsp` は 16 の倍数に戻ります。そのあとの `sub rsp, N` では N を 16 の倍数にします。
- Windows では、さらに 32 バイトのシャドウ領域も確保します。

## 3.8 最適化で C のソースと対応しない

**症状**: `-O2` でビルドしたものを読むと、ループが展開されていたり、関数が消えていたりして、ソースと結びつかない。

**原因**: 最適化では、インライン展開・ループ展開・SIMD 化・計算の前倒し・使われない処理の削除などが行われます。

**解き方**

1. 最初は `-O0` か `-O1` で、ソースとの対応を確認しながら読みます。
2. `-g` を付けて `objdump -d -S` で出力すると、ソース行がアセンブリの間に表示されます。
3. Compiler Explorer では、ソースの行とアセンブリの対応が色分けで表示されます。
4. 関数が消えて見えるときは、呼び出し元にインライン展開されていないか確認します。

## 3.9 `xor eax, eax` などの「慣用句」

意味が分かりにくいのに、頻繁に出てくる書き方です。

| 書き方 | 意味 |
|-------|------|
| `xor eax, eax` | `eax` = 0（`mov eax, 0` より命令が短い） |
| `test eax, eax` + `je` | `eax == 0` なら飛ぶ |
| `test eax, eax` + `js` | `eax < 0`（符号付き）なら飛ぶ |
| `lea eax, [rdi+rsi]` | `eax = rdi + rsi`（足し算） |
| `sar eax, 31` | 負なら -1、0 以上なら 0（符号の取り出し） |
| `nop` / `nop DWORD PTR [rax+0x0]` | 何もしない（ループ先頭などの位置合わせ） |
| `endbr64` | 不正な間接ジャンプを防ぐ仕組み（CET）の目印。処理には影響しない |
| `call ... @plt` | 共有ライブラリの関数呼び出し（`printf@plt` など） |

## 3.10 練習の進め方

1. 短い C の関数（足し算、if、for）を Compiler Explorer に貼り、`-O0` と `-O2` の両方で見比べます。
2. 出力された命令を 1 行ずつ、この資料の表と照らし合わせて C に戻します。
3. 慣れてきたら GDB で `stepi` を使って 1 命令ずつ実行し、`info registers` で値の変化を確認します。
