> フォレンジック調査は「残っている記録」でしかできません。OWASP の資料は、**あとで調査できるように、アプリがログを正しく残すこと** を扱っています。

## 2.1 なぜログがフォレンジックの土台になるのか

- OWASP Top 10:2025 の A09 は、ログを **「遅れて行うフォレンジック分析」に使えるだけの期間** 保存するよう求めています。
- 同じ項目では、ログや監視がなかったために侵害に長い間気づけなかった事例が挙げられています（ある医療保険の事業者では、侵害が 2013 年から続いていた可能性があるとされています）。
- ログが残っていない・改ざんされている・時刻がずれている、のどれかがあると、何が起きたかを示せなくなります。

## 2.2 記録すべきイベント（Logging Cheat Sheet）

OWASP は、次のイベントを「可能な限り記録する」よう挙げています。

| 分類 | 例 |
|------|----|
| 入力・出力の検証の失敗 | 形式が不正な値、文字コードの不正、出力の検証エラー |
| 認証 | ログインの **成功と失敗** |
| 認可（アクセス制御） | 権限のない操作の失敗 |
| セッション管理 | セッション ID の値の改ざんなど |
| アプリケーションのエラー、システムのイベント | 実行時のエラー、接続の問題、起動・停止 |
| 危険度の高い機能の利用 | ユーザーの追加・削除・権限変更、管理者の操作、既定・共有アカウントの利用、機密データへのアクセス、暗号鍵の操作、データのインポート・エクスポート、ファイルのアップロード、デシリアライズの失敗 |
| 業務ロジックの不正 | 想定外の順序での操作など |

> 記録が多すぎて重要な警告が埋もれる状態（OWASP は「alarm fog」と呼んでいます）にも注意します。

## 2.3 1件のログに入れる項目：いつ・どこで・誰が・何を

OWASP は、各イベントに **when・where・who・what** を記録するよう求めています。

| 項目 | 内容 | 例 |
|------|------|----|
| **When（いつ）** | ログを書いた日時、イベントが起きた日時、一連の処理を結び付ける ID | `2026-11-16T10:23:45+09:00`、リクエスト ID |
| **Where（どこで）** | アプリの名前と版、サーバーのアドレス、画面や API のエンドポイント、コードの場所 | `shop-api v2.1`、`/login` |
| **Who（誰が）** | 接続元のアドレス、ユーザーの識別子 | `198.51.100.7`、`user_id=1024` |
| **What（何を）** | イベントの種類、重要度、説明、結果 | `authn_login_fail`、`WARN` |

!!! note "時刻は ISO 8601 形式で、UTC とのずれを付ける"
    Logging Vocabulary Cheat Sheet は、日時を **UTC とのずれ（オフセット）付きの ISO 8601 形式** で記録するよう求めています（例：`2021-01-01T01:01:01-0700`）。Logging Cheat Sheet も、すべてのサーバーや機器の時刻を同期するよう求めています。同期できない機器では、時刻のずれを測るか、時刻の信頼度を記録します。

## 2.4 記録してはいけないデータ

ログは多くの人や仕組みに読まれるため、次のデータは **そのまま記録せず**、削除・マスク・ハッシュ化・暗号化します（Logging Cheat Sheet）。

| 記録しない | 理由 |
|----------|------|
| パスワード | ログから漏れると、そのまま不正ログインに使われる |
| セッション ID、アクセストークン | 漏れるとセッションを乗っ取られる（必要ならハッシュ化する） |
| 暗号鍵、DB の接続文字列 | システム全体が危険になる |
| クレジットカードの情報 | 規制の対象 |
| 機密性の高い個人情報 | 個人情報の漏えいになる |
| ソースコード | 内部の構造が知られる |

ファイルのパス、内部のアドレス、機密性の低い個人情報も、場合によって特別な扱いが必要とされています。法律で集めることが許されない情報は、記録しません。

```text
NG：login failed user=taro password=<pass>          ← パスワードを記録している
OK：authn_login_fail:taro src=198.51.100.7          ← 何が起きたかだけを記録
```

## 2.5 ログそのものを守る

ログが攻撃者に消されたり書き換えられたりすると、証拠として使えなくなります。OWASP は次の対策を挙げています。

| 対策 | 内容 |
|------|------|
| 改ざんの防止と検出 | 保存後に改ざんされていないかを検出できるようにする。早めに読み取り専用の媒体に移す |
| 安全な転送 | ログを別のサーバーに送るときは、TLS で保護した syslog などの安全な方法を使う |
| 別の場所への保存 | ログがそのサーバーの中にしかないと、サーバーを乗っ取られたときに一緒に消される（A09 の問題例） |
| アクセスの制限と記録 | ログを読める人を絞って定期的に見直す。ログへのアクセス自体も記録・監視する |
| 保存期間 | 決められた期間より前に消さず、期間を過ぎたら保持しない（期間は法律・規制・契約で決まる） |

!!! warning "ログインジェクションに注意"
    利用者の入力をそのままログに書くと、改行（CR / LF）を入れられて、偽のログ行を作られるおそれがあります（OWASP Top 10 A09 に対応する CWE-117）。OWASP は、JSON などの **構造化ログ** を使うことを勧めています。

    ```text
    利用者の入力：taro\n2026-11-16T10:00:00+09:00 authn_login_success:admin
    素朴に書いたログ：
      authn_login_fail:taro
      2026-11-16T10:00:00+09:00 authn_login_success:admin   ← 偽の成功記録に見える
    ```

## 2.6 イベント名をそろえる（Logging Vocabulary）

イベントの名前を全員で同じ形にしておくと、検索や警告の設定が簡単になります。OWASP の Logging Vocabulary Cheat Sheet は、次の形式を提案しています。

```text
カテゴリ_イベント名[:項目1,項目2,...]
```

| イベント名 | 意味 | 重要度の例 |
|-----------|------|-----------|
| `authn_login_success[:userid]` | ログインに成功 | INFO |
| `authn_login_fail[:userid]` | ログインに失敗 | WARN |
| `authn_login_fail_max[:userid,maxlimit]` | 失敗の回数が上限に達した | — |
| `authn_password_change_fail` | パスワードの変更に失敗 | CRITICAL |
| `authn_impossible_travel` | ありえない移動（短時間で遠く離れた場所からログイン） | CRITICAL |
| `authz_fail[:userid,resource]` | 権限のない操作 | CRITICAL |
| `session_created[:userid]` | セッションを作成 | — |
| `input_validation_fail:[(fields),userid]` | 入力の検証に失敗 | — |
| `malicious_sqli`（項目：userid または IP、parameter、ruleid、useragent） | SQL インジェクションの疑い | — |

カテゴリには、`authn`（認証）、`authz`（認可）、`session`、`input`、`malicious`（攻撃の疑い）、`privilege`（権限の変更）、`upload`、`user`（ユーザー管理）、`sys`（システム）などがあります。

> 重要度の欄の「—」は、今回確認した範囲では重要度の記載を確認できなかったものです。

```json
{"datetime": "2026-11-16T10:23:45+09:00", "appid": "shop-api", "event": "authn_login_fail:taro",
 "level": "WARN", "source_ip": "198.51.100.7", "request_uri": "/login"}
```

## 2.7 A09:2025 ログと警告の失敗

OWASP Top 10:2025 の9番目は **A09:2025 Security Logging and Alerting Failures（セキュリティのログと警告の失敗）** です。2021年版から、警告（アラート）の重要性を強調する名前に少し変わっています。

### 問題の例

- ログインの失敗など、記録すべきイベントが記録されていない、または記録の仕方がばらばら
- ログが改ざんから守られていない
- ログが監視されていない、警告の基準やエスカレーションの手順がない
- ログがそのサーバーの中にしかなく、バックアップされていない
- 誤検知が多すぎて、重要な警告が埋もれる
- 個人情報などをログに記録している
- ログの出力が正しくエスケープされておらず、ログを処理する仕組みが攻撃される

### 対策（OWASP が挙げているもの）

- 認証・アクセス制御・入力検証の失敗を、ユーザーの情報付きで記録し、**遅れて行うフォレンジック分析に十分な期間** 保存する
- セキュリティの仕組みの **成功と失敗の両方** を記録する
- ログを正しくエスケープ（エンコード）する
- 追記しかできないテーブルなどで、監査証跡の改ざんを防ぐ
- 疑わしい動きに警告を出し、SOC（監視チーム）が対応する手順（プレイブック）を用意する
- ハニートークン（攻撃者だけが触るおとりのデータ）を置く
- インシデント対応の計画を作る（OWASP は NIST SP 800-61r2 などを例に挙げています）

## 2.8 調査でログを読むときのポイント

上の考え方で残されたログを、調査ではこう使います。

| 見るもの | 何を探すか | 関連する章 |
|---------|----------|----------|
| 認証の失敗が急に増えた時間帯 | 総当たり攻撃の始まり | [Linux 6章 6.5](../linux/06-log-processing.md) |
| 失敗が続いた後の成功 | 攻撃が成功した可能性 | [Linux 3章 3.5](../linux/03-logs.md)、[Windows 3章 3.3](../windows/03-logs.md) |
| `authz_fail`（権限のない操作） | 権限を超えたアクセスの試み | — |
| 権限の変更・ユーザーの追加 | 攻撃者が足場を作った跡 | [Windows 3章](../windows/03-logs.md) の 4720 / 4732 |
| ログの欠け・消去の記録 | 証拠隠滅の跡 | [Windows 3章](../windows/03-logs.md) の 1102 |
| 同じリクエスト ID・セッション | 1人の操作の流れ（タイムライン） | — |

- 複数のサーバーのログを、**時刻をそろえて**（UTC に直して）1本のタイムラインに並べます（[1章 1.8](01-basics.md)）。
- 調べる前にログをコピーしてハッシュ値を記録し、解析はコピーに対して行います（[1章 1.7](01-basics.md)）。
